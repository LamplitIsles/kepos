Kepos / User guide

Use Kepos to share and connect

A publisher owns a service and decides which trusted devices may open it. A subscriber receives those selected services at local URLs or ports. Kepos has no account system and never requires one device to copy its secret identity to another.

01 Share services from this deviceSet up a desktop publisher, choose services, and approve a subscriber. 02 Connect to shared servicesInstall a subscriber, pair one publisher, and open the first local service.

macOS and Windows can act as publishers, subscribers, or both. Android is a subscriber-only app.

01 / Install

Platforms and installation

All three current artifacts remain available. The small recommendation follows a recognized browser platform; it never hides a choice or redirects a download.

Optional: verify a downloaded release before opening it. The reference covers the release manifest, SHA-256 checks, and Minisign signature.

Android subscriber

The release APK targets Android 12 and newer on arm64-v8a. Sideload it, approve the device's request to install from that source if Android asks, and start the foreground service from the app. Android does not publish services, install a VPN, or provide a TUN interface.

Apple Silicon macOS

Unzip the release and open Kepos.app. The app is ad-hoc signed and not notarized, so macOS Gatekeeper may warn on first launch. This is a local preview, not a Developer ID or Mac App Store package.

Windows desktop

Extract the ZIP as a complete Kepos\ tree. Launch App\Kepos.exe for a portable run, or use Install.cmd for the supported per-user installation. Windows 10 requires x64 build 19045 (22H2) or later. The ZIP includes Windows App Runtime files, but WebView2 and the Microsoft Visual C++ Redistributable remain system prerequisites. SmartScreen and Defender Firewall prompts are expected boundaries for this unsigned-by-Authenticode preview.

Android is sideload-only. macOS is ad-hoc signed and not notarized. Windows is not Authenticode-signed. These are packaging warnings; a failed release check is not an expected packaging warning.

02 / Connecting device

Connect as a subscriber

A subscriber does not publish a port of its own. It owns a separate device identity, pins the intended publisher, and receives only the services that publisher makes available.

  1. Install and start

    Install the artifact for the device you will carry. The packaged desktop bootstrap creates a default config and subscriber identity when absent; Android creates its identity in app-private storage. Existing config and identities are preserved.

  2. Pair one publisher

    For the interactive flow, open Add device on a running macOS or Windows desktop publisher and scan its two-minute QR invitation with Android. The publisher sees the candidate's label, platform, and subscriber-key fingerprint before you choose Allow or Deny.

    A desktop subscriber currently uses the Connect this subscriber form and the publisher's public key. Desktop QR deep-link receipt is not part of this release, so a desktop browser or app should not be expected to scan the Android invitation automatically.

  3. Read the connection state

    Connecting means the subscriber is attempting the pinned publisher connection. Connected means the registry can be refreshed. Reconnecting keeps local listeners in place while the outer connection is replaced; active client streams still need their own retry.

Open the first service

Once the registry is current, an HTTP service normally appears at http://<service-id>.localhost:17480/, for example http://navidrome.localhost:17480/. Kepos can open a web action or copy the local URL for a media client. SSH and other raw TCP services use the local listener configured for that subscriber; use the address and port shown by the app rather than assuming a universal port. 

ssh -p <configured-local-port> 127.0.0.1

Pairing is not key copying. The QR carries a short-lived invitation. The subscriber's secret identity remains on the subscriber; the publisher persists only the subscriber public key after approval.

03 / Service owner

Publisher (Desktop)

Use the packaged macOS or Windows app when the service owner wants a graphical relationship view. The desktop app reads its publisher policy from TOML and keeps the publisher identity on that machine.

Configure the packaged app

The packaged app uses the normal Kepos configuration file: ~/.config/kepos/config.toml on macOS unless XDG_CONFIG_HOME is set, and %APPDATA%\Kepos\config.toml on Windows. Edit the file before launch when you need to enable publishing or change the services. There is no graphical service editor in this preview. 

[publisher]
enabled = true
display_name = "Home"
allow = []

[[publisher.services]]
id = "navidrome"
name = "Navidrome"
target_port = 4533

List loopback TCP targets that already run on the publisher device. An empty allow list starts in deny-all mode; approving a device later adds its public key to the running policy.

Let startup create the identity

When enabled = true, desktop startup derives publisher setup from the display name, allowlist, and services in this configuration. If publisher identity is absent, the app creates it automatically before starting the role. On later launches it validates the existing policy and reuses the same identity; it never silently replaces a seed. Keep that identity on the publisher device and do not copy secret files to another machine.

Launch and approve a device

  1. Keep the app running

    Open Kepos and leave it in the macOS menu bar or Windows notification area while it publishes.

  2. Choose Add device

    Generate the invitation and let the subscriber scan it. The invitation expires after two minutes.

  3. Inspect, then Allow

    Check the label, platform hint, and public-key fingerprint. Allow persists the subscriber public key, updates the live allowlist, and promotes the same connection without restarting.

Closing the desktop window hides it. Choose Quit Kepos to stop publishing. If the configuration and identity are already present, relaunching preserves them rather than creating a new publisher.

Operators who need a headless host should use the separate Publisher (CLI) guide instead.

04 / Headless service owner

Publisher (CLI)

Use this path for repository checkouts, Nix or container hosts, and other headless environments. It owns explicit state directories, manual public-key exchange, and command-line lifecycle management.

Check out and initialize

From a Kepos repository checkout, create publisher state with the CLI setup command:

npm run kepos -- setup publisher \
  --state <publisher-state-directory> \
  --display-name Home \
  --service navidrome:Navidrome:4533

The command writes the publisher manifest and identity into the explicit state directory. Repeat it only with the same display name, services, and allowlist; an existing identity is validated, not rotated.

Manage TOML and manual keys

A headless TOML policy can keep the publisher role enabled, define the allowlist, and describe the TCP services. For a manual subscriber, create its identity, send only its public key to the publisher, then pin the publisher public key on the subscriber: 

npm run kepos -- setup subscriber \
  --state <subscriber-state-directory>

npm run kepos -- publisher key \
  --state <publisher-state-directory>

npm run kepos -- subscriber set-publisher \
  --state <subscriber-state-directory> \
  --label Home \
  --publisher-key <publisher-public-key>

Keep publisher seeds and subscriber secret keys on their originating devices. State directories are private identity storage, not configuration snippets to copy between hosts.

Run and update a headless publisher

npm run kepos -- publisher run \
  --state <publisher-state-directory> \
  --config <config.toml>

The headless process reads its policy at startup. Restart publisher run after changing an allowlist or service policy. Use the repository's Nix, container, Windows, and NUC deployment guides for process supervision and platform-specific lifecycle details.

CLI initialization is intentionally separate from packaged desktop startup. Do not use a repository checkout or a command-line state directory to repair a desktop identity; fix the desktop TOML and let the packaged app validate its own state.

For role commands, Nix and container deployment, Windows packaging, and the transport model, read the developer architecture guide, CLI guide, and deployment guide.

05 / Identity and boundary

Public keys move; secrets stay home

Kepos uses device-owned identities rather than an account or shared bearer token. Publisher authorization remains local to the publisher that owns the service.

Separate identities
Publishers and subscribers each keep their own key pair. A displayed long hexadecimal key is public.
Local approval
The publisher's allowlist and optional per-service allowlist decide what an approved subscriber may open.
No secret copies
Keep publisher seeds and subscriber secret keys in the private storage that generated them. Do not put identity files in logs.

What startup owns

A packaged desktop first run creates its default config and enabled role identities only when those pieces are absent. It creates publisher identity from enabled publisher policy and creates subscriber identity for the subscriber role. Android creates and preserves its subscriber identity in app-private storage. Existing state is validated and reused; setup does not rotate it.

In the manual flow, share the subscriber public key with the publisher and enter or pin the publisher public key on the subscriber. Pairing automates that public-key exchange for the supported desktop publisher-to-Android flow; it never transfers secret material.

Trust in one publisher does not turn the subscriber into a member of a LAN or expose unlisted ports.

06 / Why this shape

Keep the app; change the route

Kepos changes how a selected service is distributed, not what the service is. That keeps mature software's capabilities and client experience intact.

  1. Keep mature applications

    Navidrome, Jellyfin, Forgejo or Gitea, SSH, and other self-hosted services continue to run as ordinary local applications.

  2. Change service distribution

    Kepos carries selected TCP service byte streams through an authenticated direct peer connection with named channels.

  3. Preserve clients

    A browser opens a local URL, a media client receives a local address, a Git client uses its normal endpoint, and SSH uses a loopback port.

“P2P” describes Kepos's authenticated access channel, not every application protocol. The current service path is TCP-only. HyperDHT and UDX use UDP as the outer Internet carrier, while local TCP ends at each Kepos peer.

07 / A respectful comparison

Kepos and Holesail

Both projects offer direct encrypted peer-to-peer access without requiring a public service port. The useful distinction is the unit of sharing and the transport boundary each project documents.

On narrow screens, scroll horizontally to see all columns.

Kepos and Holesail comparison
Dimension Kepos Holesail
Unit of sharing A persistent publisher/subscriber device relationship with a named service registry. The official workflow starts a server for a local port and gives a client a connection key or QR flow.
Authorization Separate device-owned identities, a pinned publisher key, publisher allowlists, and optional per-service allowlists. The documented connection-key model lets the holder of the key connect to the shared tunnel.
Multiple services Several named services can use independent channels over one authenticated outer connection and appear through native actions or local listeners. The documented quickstart is port-oriented: start a port with holesail --live <PORT>, then connect with the resulting key.
Protocol boundary The current Kepos service path is TCP-only, including its split local TCP byte-stream proxy. Holesail's official repository and docs explicitly describe TCP and UDP support.
Best fit Long-lived trusted devices sharing named services with visible local presentation and per-service policy. A quick direct tunnel for a chosen port, including use cases that need UDP.

These are different tools for different needs, not a benchmark or a claim of affiliation. Read Holesail's current primary sources for its own behavior:

  • Holesail official repository — overview and API flags.
  • Holesail official overview — server/client and key or QR workflow.
  • Holesail server guide — port-oriented startup and connection options.

08 / When it does not connect

Find the boundary

Kepos's current direct path needs usable outbound UDP and a NAT pair that HyperDHT can punch. A connecting label is not proof of a specific packet failure, so check the observable boundary in order.

Configured but still Connecting

  1. Confirm the subscriber's pinned publisher public key is the key shown by the intended publisher.
  2. Confirm the publisher is running and its subscriber public key is in the publisher allowlist. An empty allowlist denies everyone.
  3. Keep the desktop process alive in the tray or menu bar; closing the window hides it but does not publish after a full quit.
  4. Wait for a direct attempt to finish, then check local diagnostics rather than copying state files or secrets into a report.

Firewall, VPN, or TUN interference

On Windows, allow Kepos through Windows Defender Firewall on the networks where the session needs DHT connectivity. Kepos does not open a public TCP service port and does not automatically bypass a firewall. VPN or TUN software can intercept or block the UDP path; test its documented bypass or pause behavior only if you control that device and understand the consequence. Kepos does not promise a relay fallback.

Bootstrap and configuration

Packaged desktop releases include bootstrap endpoints for a fresh default config. A configured [network].bootstrap list takes precedence over that packaged default; verify each host and UDP port is reachable from both peers. In the CLI, an empty bootstrap list selects HyperDHT defaults. A bootstrap node helps a peer enter the DHT; it does not authorize a subscriber or carry the service stream.

Allowlist and policy edits

A desktop Add device approval updates the live publisher. A headless TOML edit does not: restart the headless publisher run process after changing the publisher allowlist or service policy. A per-service allowlist can be narrower than the publisher-wide list, so an approved device may still be unable to open one service.

Installation warnings

Android sideload prompts, macOS Gatekeeper warnings, and Windows SmartScreen warnings are expected for these release boundaries. Windows also needs WebView2 and the Microsoft Visual C++ Redistributable; the release ZIP does not bundle them.

Copy sanitized diagnostics

On desktop, open Settings and choose Copy diagnostics. The summary is bounded and sanitized for support: it can describe roles, states, observations, and counters, but omits secret identity material, pairing tokens, and candidate IP addresses. Do not paste config or state files into a bug report.

Kepos does not provide relay fallback, generic firewall bypass, UDP service transport, or a virtual subnet. If the current UDP direct path is unavailable, the safe next action is diagnosis, not a claim that another path will take over.

The repository's CLI and network guide records state paths, listener behavior, observations, and current transport limits.
