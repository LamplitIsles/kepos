KEPOS / USER GUIDE

Share services.Connect without a subnet.

A publisher is the device that owns a service and decides which trusted devices may open it. A subscriber is the device that receives those selected services at local URLs or ports. There is no Kepos account and no identity sharing between devices.

Android subscriber

The release APK targets Android 12 and newer on arm64-v8a. Install it as a sideloaded APK, approve the device's request to install from that source if Android asks, and start the foreground service from the app. Android does not publish services, install a VPN, or provide a TUN interface.

Apple Silicon macOS

Unzip the release and open Kepos.app. The app is ad-hoc signed and not notarized, so macOS Gatekeeper may warn on the first launch. Continue only with the release verification completed; the app is a local preview, not a Developer ID or Mac App Store package.

Extract the ZIP as a complete Kepos\ tree. Launch App\Kepos.exe for a portable run, or use Install.cmd for the supported per-user installation. Windows 10 requires x64 build 19045 (22H2) or later. Preview boundary

Desktop lifecycle

Closing the desktop window hides it. Keep Kepos alive in the macOS menu bar or Windows notification area while a publisher or subscriber is in use; choose Quit Kepos to stop roles.

02 / TRUST THE DOWNLOAD

Verify first.
Then open it.

The versionless links above point to GitHub's latest stable release. They do not select prereleases. The verification tools are recommended, but you can read the setup path before installing Minisign.

  1. 01

    Keep one release together

    Download the three platform artifacts, SHA256SUMS, and SHA256SUMS.minisig from the same stable GitHub release.

  2. 02

    Verify the manifest

    Use the public key committed at release/minisign.pub; do not trust a checksum manifest whose signature fails.

    minisign -Vm SHA256SUMS \
  -x SHA256SUMS.minisig \
  -p /path/to/kepos/release/minisign.pub
  3. 03

    Check the artifact digest

    On macOS or Linux, compare every downloaded file with the signed manifest:

    shasum -a 256 -c SHA256SUMS

    On Windows, hash the ZIP and compare its output to the matching line in SHA256SUMS:

    Get-FileHash .\kepos-windows-x64.zip -Algorithm SHA256
Get-Content .\SHA256SUMS
What the preview means

Android uses the long-lived release certificate. macOS is ad-hoc signed and not notarized. Windows binaries are not Authenticode-signed. A platform warning is expected; a failed Minisign or SHA-256 check is not.

Release details

The complete maintainer and downloaded-release procedure lives in release and artifact verification.

03 / CONNECTING DEVICE

Connect as a
subscriber.

A subscriber does not publish a port of its own. It owns a separate device identity, pins the intended publisher, and receives only the services that publisher makes available to it.

  1. 01

    Install and start

    Install the artifact for the device you will carry. The packaged desktop bootstrap creates a default config and subscriber identity when they are absent; Android creates its identity in app-private storage. Existing config and identities are preserved.

  2. 02

    Pair one publisher

    For the interactive flow, open Add device on a running macOS or Windows desktop publisher and scan its two-minute QR invitation with Android. The publisher sees the candidate's label, platform, and subscriber-key fingerprint before you choose Allow or Deny.

    A desktop subscriber currently uses the Connect this subscriber form and the publisher's public key. Desktop QR deep-link receipt is not part of this release, so do not expect a desktop browser or app to scan the Android invitation automatically.

  3. 03

    Read the connection state

    Connecting means the subscriber is attempting the pinned publisher connection. Connected means the registry can be refreshed. Reconnecting keeps local listeners in place while the outer connection is replaced; active client streams still need their own retry.

Open the first service

Once the registry is current, an HTTP service normally appears at http://<service-id>.localhost:17480/, for example http://navidrome.localhost:17480/. Kepos can open a web action or copy the local URL for a media client. SSH and other raw TCP services use the local listener configured for that subscriber; use the address and port shown by the app rather than assuming a universal port. 

ssh -p <configured-local-port> 127.0.0.1
Pairing is not key copying

The QR carries a short-lived invitation. The subscriber's secret identity remains on the subscriber; the publisher persists only the subscriber's public key after approval.

One local outcome

Kepos ends a TCP connection at each local peer and presents the service as a local URL or port. It does not expose the publisher's whole network.

04 / SERVICE OWNER

Share from a
publisher.

A desktop publisher owns the service policy and the allowlist. Start with macOS or Windows for the graphical relationship view; use the advanced path below for a headless host.

Choose the services

The current desktop preview reads publisher policy from Kepos TOML. It does not include a graphical service editor. Create publisher state once with the supported setup command, then list the loopback TCP targets you want the desktop to publish. An empty publisher allowlist denies every subscriber until pairing approves one. 

[publisher]
enabled = true
display_name = "Home"
allow = []

[[publisher.services]]
id = "navidrome"
name = "Navidrome"
target_port = 4533

If the publisher state does not exist yet, create it from the repository checkout and keep its state on the publisher device: 

npm run kepos -- setup publisher \
  --state <publisher-state-directory> \
  --display-name Home \
  --service navidrome:Navidrome:4533

Approve a device

  1. 01

    Start the desktop

    Launch Kepos with the publisher policy. The hosted relationship shows the publisher key, connected subscribers, and the services published here.

  2. 02

    Choose Add device

    Generate the invitation and let the subscriber scan it. The invitation expires after two minutes and an unknown device can read only the pairing channel while it waits.

  3. 03

    Inspect, then Allow

    Check the label, platform hint, and public-key fingerprint. Allow persists the subscriber public key, updates the live allowlist, and promotes the same connection without a publisher restart or second pairing connection.

Policy changes

Desktop pairing is live: its approval updates the running desktop publisher and its TOML-owned policy. A headless publisher reads TOML at startup, so restart publisher run after changing an allowlist or service. Never copy a publisher seed or subscriber secret key to make a second device.

Desktop roles

macOS and Windows may run publisher, subscriber, or both. The roles retain separate state and keys even when the desktop process shares one HyperDHT node.

Keep the host alive

A publisher is the service owner. Closing its window is not the same as quitting; leave the menu-bar or notification-area process running while subscribers need access.

05 / IDENTITY AND BOUNDARY

Public keys move.
Secrets stay home.

Kepos uses device-owned identities rather than an account or shared bearer token. Publisher authorization remains local to the publisher that owns the service.

Separate identities

Publishers and subscribers each keep their own key pair. A displayed long hexadecimal key is public.

Local approval

The publisher's allowlist and optional per-service allowlist decide what an approved subscriber may open.

No secret copies

Keep publisher seeds and subscriber secret keys in the state directory that generated them. Do not put state files in logs.

What startup owns

A packaged desktop first run creates its default config and subscriber identity only when those pieces are absent. Android creates and preserves its subscriber identity in app-private storage. Existing state is validated and reused; setup does not rotate it. Publisher state is created separately by publisher setup and is also preserved by the desktop runtime.

In the manual flow, share the subscriber public key with the publisher and enter or pin the publisher public key on the subscriber. Pairing automates that public-key exchange for the supported desktop publisher to Android flow; it never transfers secret material.

Service scope

Trust in one publisher does not turn the subscriber into a member of a LAN or expose unlisted ports.

06 / WHY THIS SHAPE

Keep the app.
Change the route.

Kepos changes how a selected service is distributed, not what the service is. That keeps mature software's capabilities and client experience intact.

Keep mature applications

Navidrome, Jellyfin, Forgejo or Gitea, SSH, and other self-hosted services continue to run as ordinary local applications.

Change distribution

Kepos carries selected TCP service byte streams through an authenticated direct peer connection with named channels.

Preserve clients

A browser opens a local URL, a media client receives a local address, a Git client uses its normal endpoint, and SSH uses a loopback port.

Transport boundary

“P2P” describes Kepos's authenticated access channel, not every application protocol. The current service path is TCP-only. HyperDHT and UDX use UDP as the outer Internet carrier, while local TCP ends at each Kepos peer.

07 / A RESPECTFUL COMPARISON

Kepos and Holesail.
Different fits.

Both projects offer direct encrypted peer-to-peer access without requiring a public service port. The useful distinction is the unit of sharing and the transport boundary each project documents.

Dimension Kepos Holesail
Unit of sharing A persistent publisher/subscriber device relationship with a named service registry. The official workflow starts a server for a local port and gives a client a connection key or QR flow.
Authorization Separate device-owned identities, a pinned publisher key, publisher allowlists, and optional per-service allowlists. The documented connection-key model lets the holder of the key connect to the shared tunnel.
Multiple services Several named services can use independent channels over one authenticated outer connection and appear through native actions or local listeners. The documented quickstart is port-oriented: start a port with holesail --live <PORT>, then connect with the resulting key.
Protocol boundary The current Kepos service path is TCP-only, including its split local TCP byte-stream proxy. Holesail's official repository and docs explicitly describe TCP and UDP support.
Best fit Long-lived trusted devices sharing a selected set of named services with visible local presentation and per-service policy. A quick direct tunnel for a chosen port, including use cases that need UDP.

These are different tools for different needs, not a benchmark or a claim of affiliation. Read Holesail's current primary sources for its own behavior:

  • Holesail official repository — overview and API flags.
  • Holesail official overview — server/client and key or QR workflow.
  • Holesail server guide — port-oriented startup and connection options.

08 / WHEN IT DOES NOT CONNECT

Find the boundary.
Take the next safe step.

Kepos's current direct path needs usable outbound UDP and a NAT pair that HyperDHT can punch. A connecting label is not proof of a specific packet failure, so check the observable boundary in order.

Configured but still Connecting

  1. Confirm the subscriber's pinned publisher public key is the key shown by the intended publisher.
  2. Confirm the publisher is running and its subscriber public key is in the publisher allowlist. An empty allowlist denies everyone.
  3. Keep the desktop process alive in the tray or menu bar; closing the window hides it but does not publish after a full quit.
  4. Wait for a direct attempt to finish, then check the local diagnostics rather than copying state files or secrets into a report.

Firewall, VPN, or TUN interference

On Windows, allow Kepos through Windows Defender Firewall on the networks where the session needs DHT connectivity. Kepos does not open a public TCP service port and does not automatically bypass a firewall. VPN or TUN software can intercept or block the UDP path; test its documented bypass or pause behavior only if you control that device and understand the consequence. Kepos does not promise a relay fallback.

Bootstrap and configuration

Packaged desktop releases include bootstrap endpoints for a fresh default config. A configured [network].bootstrap list takes precedence over that packaged default; verify each host and UDP port is reachable from both peers. In the CLI, an empty bootstrap list selects HyperDHT defaults. A bootstrap node helps a peer enter the DHT; it does not authorize a subscriber or carry the service stream.

Allowlist and policy edits

A desktop Add device approval updates the live publisher. A headless TOML edit does not: restart the headless publisher run process after changing the publisher allowlist or service policy. A per-service allowlist can be narrower than the publisher-wide list, so an approved device may still be unable to open one service.

Installation warnings

Android sideload prompts, macOS Gatekeeper warnings, and Windows SmartScreen warnings are expected for these release boundaries. Finish the Minisign and SHA-256 checks first. Windows also needs WebView2 and the Microsoft Visual C++ Redistributable; the release ZIP does not bundle them.

Copy sanitized diagnostics

On desktop, open Settings and choose Copy diagnostics. The summary is bounded and sanitized for support: it can describe roles, states, observations, and counters, but it omits secret identity material, pairing tokens, and candidate IP addresses. Do not paste config or state files into a bug report.

Not a promise

Kepos does not provide relay fallback, generic firewall bypass, UDP service transport, or a virtual subnet. If the current UDP direct path is unavailable, the safe next action is diagnosis, not a claim that another path will take over.

Deeper operator detail

The repository's CLI and network guide records state paths, listener behavior, observations, and the current transport limits.

09 / ADVANCED PUBLISHERS

Manual keys.
Headless hosts.

Use this path for CLI, Nix, container, or NUC publishers that do not have the desktop Add device surface. It is an explicit public-key flow, not a second graphical onboarding product.

Manual public-key flow

  1. 01

    Create the subscriber identity

    npm run kepos -- setup subscriber \
  --state <subscriber-state-directory>

    Copy only the printed subscriber public key to the publisher operator.

  2. 02

    Allow the subscriber

    Add that public key to the publisher's allow list and configure each TCP service. An empty list is deny-all.

  3. 03

    Pin the publisher

    npm run kepos -- publisher key \
  --state <publisher-state-directory>

npm run kepos -- subscriber set-publisher \
  --state <subscriber-state-directory> \
  --label Home \
  --publisher-key <publisher-public-key>
  4. 04

    Run the roles

    Start the publisher and subscriber with their existing state directories. Restart a headless publisher after TOML policy edits.

Repository paths

Use the detailed CLI guide for role commands, Nix and container deployment, and Windows packaging detail.

Never copy state

Publisher seeds, subscriber secret keys, and whole identity directories belong only on the device that created them.
